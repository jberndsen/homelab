Where Argo's responsibility begins

Checkpoint 1 was completed on 2026-10-08. This lesson records that bootstrap stage. The controller and key-recovery stage is covered in lesson 2; current rollout status is in the plan's progress section.

Your goal is to operate this media stack through Git while keeping its data recoverable. This first step gives Argo a place to run. Application adoption comes later.

Now: laptop → kubectl + Kustomize → namespaces, NAS PV, Argo installation.

Later: Git → ApplicationSet → Applications → media and Sealed Secrets resources.

Read the files as a chain of responsibility

cluster/namespace/argocd-namespace.yaml creates a Namespace: the group containing Argo's resources. We create it manually, alongside media, so Application deletion will not own its lifecycle.

ns-argo/kustomization.yaml combines the pinned upstream installation with our HTTP ConfigMap patch and Traefik Ingress. Kustomize produces ordinary Kubernetes YAML; it does not run a controller.

The upstream installation includes CRDs for Application, ApplicationSet and AppProject. A CRD registers an API type. Controllers are the running processes that watch those objects and work toward their desired state. That is why CRD registration must finish before we apply an ApplicationSet.

Try explaining these before opening the answers

You push an edit to ns-argo/ingress.yaml. What makes it reach the cluster?

A manual kubectl apply --server-side -k infrastructure/node-main/ns-argo. Argo does not manage its own bootstrap files in this design.

All Argo Pods are Ready. Does that mean media is managed through Git?

No. Ready Pods show the Argo processes are running. We still need Applications, successful rendering and deliberate adoption before Argo owns media reconciliation.

Why preserve a PVC's UID as well as its name during adoption?

A deleted and recreated claim can have the same name and a different UID. Checking UIDs, PV bindings and volume paths lets us detect storage replacement.
