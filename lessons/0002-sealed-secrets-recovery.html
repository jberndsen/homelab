Homelab · Lesson 02 · About five minutes

What makes an encrypted secret recoverable?

Your goal is to rebuild this homelab from Git while preserving credentials and data. Git contains the desired configuration. It needs separate recovery sources for secrets and application data.

Deployment: Git directory → ApplicationSet → Application → Sealed Secrets controller.

Secrets: plaintext Secret + public certificate → kubeseal → encrypted SealedSecret in Git.

Recovery: NAS .yaml.age + password-manager passphrase → private keys → recovered Secret.

Application data: independently verified Proxmox VM backup; NAS media is external.

Two controllers, two responsibilities

The ApplicationSet discovers our production folders and generates media and sealed-secrets Applications. It does not itself apply their workload manifests. Each Application describes a Git source and a destination. Automatic sync is disabled at this stage; we manually sync only Sealed Secrets. Media adoption is checkpoint 3.

The Sealed Secrets controller watches SealedSecret objects and produces ordinary Kubernetes Secret objects. Applications continue to consume those Secrets as before. Strict scope binds ciphertext to its exact Secret name and namespace.

Why we test the NAS copy

An encrypted file existing on NAS proves little by itself. We decrypt that actual copy with the saved passphrase, compare it with the exported key list, then use kubeseal --recovery-unseal to recover a harmless test value offline. We also validate the sealed test against the running controller. No production key replacement or real credential is needed for this test.

Sealing keys renew every 30 days by default. Renewal adds a key; older ciphertext still needs its older private key. Before sealing, check that the active certificate fingerprint is covered by the verified full key backup, then seal with that exact certificate using --cert.

Try these before opening the answers

You add another credential tomorrow using the same backed-up certificate. Is a new key backup needed?

No. The private key already covers ciphertext produced with its public certificate. A new sealing key requires refreshing the full backup; adding a credential alone does not.

A new sealing key appears. Can you delete the older private key?

Keep it. SealedSecrets in current or historical Git revisions can still depend on that older key. Export all controller key Secrets, and retain the previous backup until the new one is verified.

Media appears in Argo with a render error. Did discovery change its running workloads?

No. The Application exists, but automatic sync is disabled and no media sync was requested. Its ignored Secret references will be replaced during the next checkpoint.

You have Git and the sealing keys. Do you have Jellyfin's database and media files?

No. Git and keys recover configuration and credentials. Application data needs the VM backup, and NAS media needs its own independent recovery source.

Ask the agent follow-up questions about anything unclear. Before checkpoint 3, try explaining why the certificate used for sealing must be covered by the verified backup.
